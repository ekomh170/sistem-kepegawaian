Perubahan utama dari v2 ke v3

● Konsolidasi User — tabel tb_admin, tb_supervisor, dan tb_karyawan dihapus; seluruh atribut (nik, no_hp, posisi) dipindah ke tb_user. Peran tetap dibedakan via kolom role.
● Verifikasi inline — tabel tb_verifikasi dihapus; data verifikasi (status_verifikasi, diverifikasi_oleh, catatan_verifikasi, tgl_verifikasi) di-inline ke tb_presensi karena relasinya memang 1:1.
● Penyatuan Laporan & Rekap — tabel tb_rekap_presensi_bulanan + tb_laporan digabung menjadi tb_laporan_presensi dengan kolom jenis dan file_path.
● Penamaan konsisten — semua FK ke user memakai user_id (V2 sebelumnya campur karyawan_id/admin_id/supervisor_id).
● Rename Jadwal — tb_jadwal → tb_jadwal_pekerjaan agar lebih deskriptif.
● 6 tabel inti sesuai ERD v3: tb_user, tb_jadwal_pekerjaan, tb_detail_pekerjaan, tb_presensi, tb_bukti_pekerjaan, tb_laporan_presensi. Tabel tb_setting tetap dipertahankan sebagai tabel pendukung (konfigurasi sistem).

⚠ Field critical yang dipertahankan untuk backward compatibility

Gambar ERD V3 yang menjadi rujukan tidak menampilkan beberapa field yang dipakai fitur V2 saat ini. Agar fitur tidak rusak, field berikut tetap dipertahankan di schema akhir (ditandai badge KEEP):
  • tb_presensi.foto_masuk, foto_keluar — fitur upload selfie check-in/check-out
  • tb_presensi.latitude_masuk, longitude_masuk, latitude_keluar, longitude_keluar — audit GPS check-in/out
  • tb_detail_pekerjaan.alamat_lokasi, alasan_tolak — alamat tekstual lokasi tugas & alasan tolak tugas
  • tb_bukti_pekerjaan.keterangan — konteks tekstual upload bukti
  • tb_setting (tabel pendukung) — konfigurasi runtime (geofence, identitas perusahaan) yang dulu dipakai di V2
Field gaji (gaji_pokok, total_potongan, gaji_bersih) yang muncul di gambar ERD V3 untuk tb_laporan_presensi tidak diadopsi — karena fitur tampilan gaji sudah dihapus sejak V2.2. Hanya total_potongan yang dipertahankan (untuk rekap keterlambatan).

  • FK generated_by → tb_user (admin/supervisor)
  • AT judul string
  • AT periode string (YYYY / YYYY-MM / YYYY-MM-DD)
  • ENUM jenis Harian|Mingguan|Bulanan|Tahunan
  • AT jumlah_hadir int unsigned, null
  • AT jumlah_terlambat int unsigned, null
  • AT jumlah_tidak_hadir int unsigned, null
  • AT total_potongan decimal(12,2), null
  • AT file_path string, null
  • AT tgl_generate datetime
  • AT created_at timestamp
  • karyawan(): BelongsTo // user_id
  • generator(): BelongsTo // generated_by
  • hitungRekap(string): self
  • generateFile(string): string // path file CSV/Excel/PDF
Penyatuan dari tb_laporan (metadata laporan) dan tb_rekap_presensi_bulanan (rekap kalkulasi). Kolom jenis menentukan tipe periode laporan. Kolom jumlah_* dan total_potongan diisi ketika tipe laporan adalah rekap per karyawan (Bulanan). Kolom file_path berisi link file export yang sudah di-generate. Field gaji tidak diadopsi mengikuti penghapusan fitur gaji di V2.2.

Dipertahankan dari V2 — tidak masuk gambar ERD V3 tapi tetap esensial untuk konfigurasi runtime via Filament panel.

Tabel 3. Analisis Trade-off Desain V3

✓ Kelebihan ERD V3

  • Schema ramping — 7 tabel total (6 inti + 1 pendukung), turun dari 12 tabel V2.
  • Single source of truth User — tidak perlu JOIN 4 tabel (user+admin+supervisor+karyawan) untuk dapat profil lengkap.
  • Naming konsisten — semua FK ke user memakai user_id, tidak lagi campur karyawan_id/admin_id/supervisor_id.
  • Verifikasi inline — relasi 1:1 presensi↔verifikasi disederhanakan jadi kolom, mengurangi JOIN dan latensi query.
  • Laporan terunifikasi — penyatuan rekap + laporan jadi satu tabel mengurangi duplikasi konsep.
  • Penamaan lebih deskriptif — tb_jadwal menjadi tb_jadwal_pekerjaan mengisyaratkan konteks.

✗ Kekurangan / Risiko ERD V3

  • tb_user gemuk — kolom nik, no_hp, posisi yang hanya relevan untuk karyawan jadi nullable. Bisa jadi data integrity smell bila tidak ada constraint role-based.
  • Migrasi data berat — data dari 4 tabel user V2 harus di-merge ke tb_user; perlu strategi mapping yang cermat.
  • Polimorfik laporan — tb_laporan_presensi menyimpan dua bentuk record (rekap per-karyawan vs laporan agregat) — kolom user_id/jumlah_*/total_potongan jadi nullable, schema kurang strict.
  • FK self-referential tb_user — kolom dibuat_oleh, diverifikasi_oleh, generated_by semua FK ke tb_user; query get user with role jadi sering muncul.
  • Audit trail verifikasi terbatas — verifikasi inline = tidak ada history kalau supervisor mengubah keputusan (V2 punya tb_verifikasi sebagai append-only log).

🛠 Catatan Migrasi V2 → V3

Implementasi V3 memerlukan langkah migrasi berikut:
  • Backup penuh DB V2 sebelum migrasi (tb_admin, tb_supervisor, tb_karyawan, tb_verifikasi, tb_rekap_presensi_bulanan, tb_laporan akan di-drop).
  • Migration script merge user data — copy nik/no_hp/posisi/dll dari tb_admin/tb_supervisor/tb_karyawan ke kolom baru di tb_user.
  • Migration script merge verifikasi — copy status/supervisor_id/catatan/tgl_verifikasi dari tb_verifikasi ke kolom inline di tb_presensi (mapping presensi_id).
  • Migration script merge laporan + rekap — merge tb_laporan + tb_rekap_presensi_bulanan jadi tb_laporan_presensi dengan jenis & field statistik.
  • Refactor Filament Resource — KaryawanResource, AdminResource, SupervisorResource jadi UserResource tunggal dengan filter by role. RekapPresensiBulananResource + LaporanResource jadi LaporanPresensiResource tunggal.
  • Refactor RBAC — semua canViewAny/canCreate tetap by role, tapi data karyawan diambil via User::where('role','karyawan') bukan via tabel terpisah.
  • Tabel tb_setting tetap dipertahankan — tidak perlu migrasi struktur, hanya konfirmasi semua key (kantor_lat, kantor_lng, radius, toleransi, nama_perusahaan, alamat_perusahaan) masih tersedia.

⚠ Field critical dipertahankan dari V2

Walaupun gambar ERD V3 tidak menampilkannya, field berikut tetap ada di schema V3 agar fitur V2.3 saat ini tidak rusak:
  • tb_presensi.foto_masuk, foto_keluar — fitur upload selfie
  • tb_presensi.latitude_masuk/longitude_masuk/latitude_keluar/longitude_keluar — audit GPS
  • tb_detail_pekerjaan.alamat_lokasi — alamat tekstual lokasi tugas
  • tb_detail_pekerjaan.alasan_tolak — alasan tolak tugas oleh karyawan
  • tb_bukti_pekerjaan.keterangan — konteks tekstual upload bukti
  • tb_setting (tabel pendukung) — konfigurasi runtime
Field gaji_pokok/total_potongan/gaji_bersih yang muncul di gambar ERD V3 untuk tb_laporan_presensi tidak diadopsi karena fitur tampilan gaji sudah dihapus permanen sejak V2.2. Hanya total_potongan yang dipertahankan (akumulasi potongan keterlambatan).
